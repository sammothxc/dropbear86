# dropbear86

An SSH-2 client for 8086 and other 16-bit x86 CPUs running [ELKS](https://github.com/ghaerr/elks). It is a fork of [Dropbear](https://github.com/mkj/dropbear), retargeted for `ia16-elf-gcc`, built with the ELKS libc, and audited for the 16-bit integer widths the SSH protocol demands.

To the extent I've been able to check, this is the first SSH client for ELKS on 8086.

## Status

- Builds cleanly against `ia16-elf-gcc` 6.3.0 with the `elks-libc` runtime.
- KEX (Curve25519), host-key verify (Ed25519), and cipher (ChaCha20-Poly1305) all work.
- Verified end-to-end in QEMU (`hd32-fat.img` from ELKS 0.9.2, `ne2k_isa`).
- Verified end-to-end on real hardware: Compaq Portable Plus (8088 @ 4.77 MHz). Reaches the password prompt, authenticates, opens an interactive session.
- Connecting takes about 3 minutes on a 4.77 MHz 8088, down from ~35. See "Performance" below.

## Building

Prerequisites: `ia16-elf-gcc` (from [tkchia's PPA](https://launchpad.net/~tkchia/+archive/ubuntu/build-ia16/) or built from source with [`tkchia/build-ia16`](https://github.com/tkchia/build-ia16)) plus `elks-libc`.

```
make -f Makefile.elks
```

Produces `./ssh`, an ELKS medium-model a.out executable, ~125 KB. Heap is provisioned at 24 KB and stack at 4 KB (see the linker line in `Makefile.elks`). Data + bss + heap + stack come to ~46 KB of ELKS's 64 KB per-process data segment; a 40 KB heap made `execve` fail on real hardware.

The Curve25519 field arithmetic is hand-written 8086 assembly, `src/fe25519_ia16.S`, generated by `src/fe25519_ia16.py`. The `.S` is committed, so building needs no Python.

Local build knobs (algorithms enabled, feature toggles, buffer sizes) live in `localoptions.h` at the tree root. The default set is tuned for 8086: only Curve25519 / Ed25519 / ChaCha20-Poly1305 are enabled, RSA / DSS / ECDSA and all forwarding features are compiled out.

## Deploying to ELKS

Copy `ssh` into `/bin/` on an ELKS filesystem (loop-mount the disk image, `cp`, `chmod 755`) or transfer it over FTP from a running system:

```
# on the ELKS host, after net start:
ftp <your dev machine>
> binary
> get ssh /bin/ssh
> quit
chmod 755 /bin/ssh
```

Then:

```
ssh -y user@host
```

`-y` skips known-hosts prompting, which is what you want on ELKS. Persistent known-hosts is more filesystem trouble than it's worth for a device with no meaningful trust anchor.

## Performance

On a 4.77 MHz 8088 (Compaq Portable Plus), measured on real hardware:

| | Original (portable C) | Now |
|---|---|---|
| Connect, start to password prompt | ~35 min | ~3 min |
| Curve25519 scalar multiplication | 1079 s | 31 s |
| Ed25519 host-key signature verify | not timed* | 47 s |

\*Not timed on its own in pure C. With the assembly field arithmetic but the original verify algorithm, it took 136 s.

What got it there:

- 8086 assembly field arithmetic (~35×). Field elements are sixteen 16-bit limbs (the representation of µNaCl's MSP430 code), so every limb product is one hardware `MUL`; multiply and square are fully unrolled.
- Faster signature verify (~2.9×). Verification only handles public data, so it uses one shared chain of doublings with signed sliding windows instead of two constant-time ladders. Key generation and signing stay constant-time.
- No wasted key generation. When Dropbear's guessed key exchange doesn't match the server's first choice, the client reuses the already-generated X25519 key instead of making a new one (saves 31 s).

Of the remaining ~3 minutes, about 55 s is ELKS loading the binary (it reads the ~2,100 relocation entries one at a time), 62 s is two X25519 operations, and 47 s is verifying the server's signature. Interactive traffic after the handshake is symmetric-only (ChaCha20-Poly1305) and usable at keystroke speed.

Set `DROPBEAR_PHASE_TIMING=1` in the environment to print a timestamp at each handshake step. `test-crypto/mathtest` benchmarks the crypto on its own. Full measurement history is in [`PERF.md`](PERF.md).

## Known limitations

- Entropy is weak. ELKS has no `/dev/urandom`; `dbrandom.c` falls back to hashing `getpid() + gettimeofday() + clock() + /bootopts` and a couple of similar sources. A seed persisted in `/etc/dropbear.seed` accumulates entropy across connections, but the first connection after a fresh install is weak (probably 30–40 bits), and it's still no substitute for a real entropy source. Do not use this to reach anything that actually matters. An ELKS-side `/dev/urandom` is the real fix.
- Server login timeout. OpenSSH drops connections that haven't authenticated within `LoginGraceTime` (default 2 minutes, counted from the TCP connect). The password prompt arrives about 90 s after connecting, which leaves roughly 30 s to type the password; tested working against a stock OpenSSH server on the Compaq.
- Password auth only in practice. Public-key auth is compiled in, but signing with an Ed25519 key still uses the slow constant-time path and would push past the default 2-minute `LoginGraceTime`; it also hasn't been tested with a private key stored on an ELKS filesystem.
- Slow startup. ELKS takes about 55 s to load `ssh` before it runs at all (relocation processing), so even `ssh -V` takes nearly a minute on an 8088.

## Provenance

Based on [Dropbear](https://github.com/mkj/dropbear) by Matt Johnston, specifically its development branch shortly after the 2025.89 release (upstream commit [`8b579571`](https://github.com/mkj/dropbear/commit/8b579571), April 2026). The ELKS retargeting work was started by the previous maintainer in [`parabyte/ssh-daemon-project`](https://github.com/parabyte/ssh-daemon-project), which was imported here as this repo's first commit and continued from there. The full upstream Dropbear source tree is retained because the QEMU test harness also builds a host-side Dropbear server fixture from the same base.

Files not in the ELKS build path (server-side code, agent forwarding, TCP forwarding, keyimport, RSA/DSS/ECDSA implementations, libtommath) are still present but unbuilt; the ia16 type audit only touched the client-side files actually compiled into `ssh`. If you want to build the host-side tools too, see `INSTALL.md` and `DEVELOPING.md` inherited from upstream.
